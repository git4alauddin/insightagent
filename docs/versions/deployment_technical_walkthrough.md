# Deployment Technical Walkthrough

## 1. Design Intent

The deployment pass is not a new product feature. It is the operational proof that the finished backend can run outside the local development environment.

The first deployment chunk focuses on two basic readiness requirements:

- avoid committing generated local artifacts
- make the container compatible with cloud runtime port injection

## 2. Files Changed

## `.gitignore`

Purpose:

- prevent local runtime state from entering Git
- keep deployment commits focused on source/config changes

Deployment-related ignores added:

```text
logs/
uploads/
insightagent.db
```

Why:

- `insightagent.db` is local SQLite runtime state
- `uploads/` contains user-uploaded runtime files
- `logs/` contains generated observability output

These should be regenerated by the running service or replaced by managed infrastructure in a production-grade deployment.

## `Dockerfile`

Purpose:

- define the container runtime for the FastAPI app

Previous command:

```text
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Updated command:

```text
uvicorn app.main:app --host 0.0.0.0 --port ${PORT:-8000}
```

Why:

- local development can still default to port `8000`
- Cloud Run can provide its own `PORT` value
- the same image works in local and cloud runtime contexts

## 3. Current Runtime Behavior

Production behavior is controlled by environment variables:

```text
APP_ENV=production
APP_VERSION=v10
DOCS_ENABLED=false
API_KEY=<service-api-key>
LLM_API_KEY=<provider-api-key>
RATE_LIMIT_ENABLED=true
```

Relevant app behavior already exists:

- `DOCS_ENABLED=false` disables `/docs`, `/redoc`, and `/openapi.json`
- `API_KEY` protects private routes through `x-api-key`
- `/health` and `/ready` remain public for deployment checks

## 6. Production CORS Startup Fix

Initial Cloud Run deployment failed with a generic container startup/port message.

Root cause:

```text
APP_ENV=production
CORS_ALLOWED_ORIGINS=*
```

The app intentionally rejects wildcard CORS origins in production. This is good production behavior, but Cloud Run surfaced it as a startup failure because the app exited before listening on `PORT=8080`.

Fix:

- Replace wildcard CORS with a non-wildcard origin value.
- Redeploy the Cloud Run revision.

Result:

- Service started successfully.
- Deployed smoke tests passed.

## 9. Interview Summary

For deployment readiness, I first cleaned the repo boundary and container runtime. I ignored local runtime artifacts like SQLite DB files, uploads, and logs so they do not get committed, and I changed the Docker startup command to respect a platform-provided `PORT` while still defaulting to `8000` locally. I built and smoke-tested the Docker image locally, pushed it to Artifact Registry through Cloud Build, deployed it to Cloud Run with Secret Manager-backed keys, fixed a production CORS configuration failure, and verified the deployed API through public and authenticated smoke tests.
