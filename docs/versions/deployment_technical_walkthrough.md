# Deployment Technical Walkthrough

## 1. Design Intent

The deployment pass is not a new product feature. It is the operational proof that the finished backend can run outside the local development environment.

The first deployment chunk focuses on two basic readiness requirements:

- avoid committing generated local artifacts
- make the container compatible with cloud runtime port injection

## 2. Files Changed

## `.gitignore`

Purpose:

- prevent local runtime state from entering Git
- keep deployment commits focused on source/config changes

Deployment-related ignores added:

```text
logs/
uploads/
insightagent.db
```

Why:

- `insightagent.db` is local SQLite runtime state
- `uploads/` contains user-uploaded runtime files
- `logs/` contains generated observability output

These should be regenerated by the running service or replaced by managed infrastructure in a production-grade deployment.

## `Dockerfile`

Purpose:

- define the container runtime for the FastAPI app

Previous command:

```text
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Updated command:

```text
uvicorn app.main:app --host 0.0.0.0 --port ${PORT:-8000}
```

Why:

- local development can still default to port `8000`
- Cloud Run can provide its own `PORT` value
- the same image works in local and cloud runtime contexts

## 3. Current Runtime Behavior

Production behavior is controlled by environment variables:

```text
APP_ENV=production
APP_VERSION=v10
DOCS_ENABLED=false
API_KEY=<service-api-key>
LLM_API_KEY=<provider-api-key>
RATE_LIMIT_ENABLED=true
```

Relevant app behavior already exists:

- `DOCS_ENABLED=false` disables `/docs`, `/redoc`, and `/openapi.json`
- `API_KEY` protects private routes through `x-api-key`
- `/health` and `/ready` remain public for deployment checks

## 4. Next Verification Flow

Local container verification proved:

```text
docker build succeeds
container starts with production-like env vars
/health returns ok
/ready reports readiness
protected endpoint without key fails
protected endpoint with key succeeds
```

Verification commands/results:

- Docker image built as `insightagent:deploy-verify`.
- Container ran with `PORT=8080` and was mapped to host port `18080`.
- `GET /health` returned `status=ok`, `service=InsightAgent`, `version=v10`.
- `GET /ready` returned `status=ready`.
- `GET /docs` returned `404` with `DOCS_ENABLED=false`.
- `POST /chat` without `x-api-key` returned `401`.
- `POST /sessions` with `x-api-key=deploy-test-key` returned a successful session response.

Next, the same behavior should be checked against the Cloud Run URL.

## 5. Storage Notes

Current local persistence:

- SQLite database at `insightagent.db`
- uploads under `uploads/`

Cloud Run note:

- local filesystem persistence is not durable across instances or revisions

Portfolio decision:

- acceptable if documented as a demo limitation
- managed database/object storage should be listed as future production work

## 7. Interview Summary

For deployment readiness, I first cleaned the repo boundary and container runtime. I ignored local runtime artifacts like SQLite DB files, uploads, and logs so they do not get committed, and I changed the Docker startup command to respect a platform-provided `PORT` while still defaulting to `8000` locally. I then built the Docker image and ran a production-like local container smoke test to verify health, readiness, disabled docs, auth failure, and authenticated session creation before moving to Cloud Run.
